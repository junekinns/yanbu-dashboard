# Phase 0 Research: 품질 감사 결과

2026-09-17, `scripts/fetch_data.py`(573줄) · `app.js` · `index.html` · `style.css` · `.github/workflows/update.yml` · `README.md` 전체를 읽고, `data/latest.json`(2026-09-16T21:17Z 생성)과 외부 소스에 실제 요청을 보내 확인한 것만 적는다. 추측은 "확인 안 됨"으로 표시.

## A. 정확성 — 배지가 사실과 다른 경우

### A1. 위성 열 감지 "최근 24h"는 실제로 24~48시간 창이다 (확인됨)

- **증거**: `fetch_data.py:210,219` — `yesterday = TODAY-1`, `last24h = sum(... if h["date"] >= yesterday)`. 즉 어제 00:00 UTC부터 지금까지. 실행 시각이 UTC 23시면 47시간 창. `latest.json` west: `last24h=7`, `daily_counts[-1](09-15)=6` → 오늘분 1건이 섞여 있음이 데이터로 확인됨.
- **영향**: 평시는 *일별* 중앙값이므로 비율이 최대 2배 부풀려진다. 위험 배지가 과민해지는 방향. 헤드라인 지표.
- **Decision**: `acq_date`+`acq_time`(UTC)으로 타임스탬프를 만들어 진짜 롤링 24시간으로 센다. `daily_counts`/`history`/`baseline`은 일별 그대로.
- **Alternatives**: 라벨을 "어제부터"로 바꾸기 — 사용자가 이해하기 어렵고 비율 왜곡은 그대로라 기각. 일별 값(어제)만 쓰기 — 오늘 오전의 사건이 내일까지 안 보여 기각.

### A2. 평시가 0이면 무슨 값이 와도 "평시" (확인됨)

- **증거**: `fetch_data.py:164-165` `ratio()`는 `baseline` falsy면 `None`; `tier_up(None)` → `labels[2]`(평시). FIRMS 중부처럼 이상 화점이 드문 권역은 90일 중앙값이 0이 될 수 있고, 공지 템포도 조용한 6주 뒤 첫 급증에서 `median([0,0,0,0,0,1])=0`.
- **현재 데이터**: 공지 템포 평시 1.5(주간 `[4,0,1,2,1,2]`의 중앙값), 이번 주 7건 → 4.67배 "급증". 극소 평시에서 비율이 요동친다.
- **Decision**: 비율 계산에만 하한 적용 — FIRMS `max(baseline, 2)`, 공지 템포 `max(baseline, 1)`. 표시되는 평시값은 실제 중앙값 유지.
- **Rationale**: FIRMS 하한 2 → 3건부터 주의, 6건부터 위험. 하한 1이면 매시간 2건짜리 "주의"가 세 권역에서 깜빡거린다. 공지는 주 단위라 1이면 충분(2건 주의, 3건 급증).
- **Alternatives**: `tier_up`에 절대 최소치 파라미터 추가 — 함수 시그니처가 넓어지고 호출부마다 값이 달라 오히려 복잡. 기각.

### A3. 외교부 공지 목록 50건 잘림 (경계 조건, 확인됨)

- **증거**: `MOFA_NOTICE_URL` `pageSize=50`, 8주 창(`fetch_data.py:297`). 이번 주만 7건. 8주×7건=56>50. 활발한 시기(정확히 이 지표가 중요한 시기)에 오래된 주가 0으로 집계되어 평시가 내려가고 "급증"이 과장된다.
- **실측**: `pageSize=100` 요청 → HTTP 200, 제목 링크 99개 반환. 서버가 받아준다.
- **Decision**: `pageSize=100`.

### A4. "최근 72시간" 로그에 5일 전 사건 (확인됨)

- **증거**: `latest.json` events에 `2026-09-12 송유관 피격`이 있고(생성 09-16), 화면 제목은 "최근 72시간". 원인은 Google News `when:3d`가 느슨한 것 + `[:15]` 캡 + stale carry-over. `renderMap`은 `since`로 거르지만 `renderEvents`(app.js:148-160)는 안 거른다.
- **Decision**: `renderEvents`도 72시간으로 거른다. 서버 쪽은 손대지 않는다(지도 7일 범위 토글이 `events`를 최대 7일까지 쓸 수 있으므로 서버 데이터는 넉넉히 두는 게 맞다).

### A5. 실험적 flights 지표의 평시 정의가 잘못됐다 (내 코드, 확인됨)

- **증거**: `fetch_data.py:529-532` 최근 120개 스냅샷의 전체 중앙값. cron은 **매시간**(`update.yml:5`)이라 120개=5일, 7개=7시간. 밤(항공편 적음)에 낮 중앙값과 비교하면 "감소"가 뜬다. `index.html` 도움말 "약 이틀"도 6시간 주기를 가정한 내 오류. `maxage=14400`은 4시간 전 위치까지 "현재"로 센다.
- **Decision**: 같은 UTC 시각(`HH`)의 과거 값 중앙값(≥3개). cap 336(14일). `maxage=900`. 도움말 수정.
- **확인 안 됨**: FR24 비공식 피드가 GitHub Actions IP에서도 200을 주는지 — 첫 Actions 실행 로그로 확인 필요. 막히면 지표를 빼는 것이 기존 원칙("수집 실패만 뜨는 지표는 없느니만 못하다").

### A6. PortWatch 최근 일자 과소집계(lag) 아티팩트 — 없음 (확인됨, 조치 없음)

- **우려**: `rolling7[-1]`이 아직 안 들어온 AIS 데이터 때문에 항상 낮으면 "끊김"이 만성 오경보가 된다.
- **실측**: 호르무즈 최근 21일 일별 `[3,4,5,2,7,3,6,3,4,3,2,2,2,6,5,6,3,5,8,2,8]` — 꼬리만 낮은 게 아니라 3주 내내 낮다(평시 338/7일 ≈ 48/일 대비). 제다 `[3,3,2,1,3,4,5,3,4,2,1,1,2,2,2,0,3,4,4,4,3]` 꼬리 하락 없음. 밥엘만데브 20~38/일 안정.
- **Decision**: 해상 교통 계산은 그대로. 지표가 보여주는 "끊김"은 데이터상 실제다.

## B. 견고성 — 하나가 죽으면 전부 죽는 경우

### B1. 예상 밖 예외 하나가 그 시간의 모든 소스를 지운다 (확인됨)

- **증거**: `fetch_events`(376-410)는 `requests.RequestException`만 잡는다. 그 안에서 부르는 `feed_items`(318-334)는 `re.search(...).group(1)`을 4번 호출 — `<title>`/`<pubDate>`/`<link>`가 없는 item이 하나만 와도 `AttributeError`. `fetch_news`는 같은 함수를 부르면서 `AttributeError, ValueError`를 잡는다(= 저자가 이미 겪었다는 뜻). `fetch_maritime`(484-505)은 PortWatch가 7행 미만을 주면 `rolling7[-1]` `IndexError` — 잡는 목록에 없음. `main()`에 가드 없음 → 스크립트 종료 코드 1 → 워크플로우 "Commit if changed" 단계 미실행 → **그 시간에는 아무 소스도 갱신되지 않고, 다음 시간까지 화면이 그대로**. docstring(12행) "실패한 소스는 이전 성공 데이터를 유지"는 이 경우 거짓.
- **Decision**: `main()`에서 각 fetch를 `safe()`로 감싸 `Exception`을 잡아 `{"ok": False, "error": "TypeName: msg"}`로 바꾼 뒤 `carry_over`. 함수 내부의 세밀한 except는 그대로(더 좋은 오류 메시지).
- **Alternatives**: 각 함수의 except 목록에 타입을 계속 추가 — 다음 예상 밖 타입에서 또 죽는다. 기각.

### B2. 번역을 매시간 다시 한다 (확인됨)

- **증거**: `fetch_telegram`(461-463) 6건 × 최대 480자를 매 실행마다 MyMemory에 보낸다. 캐시 없음. 매시간이면 하루 최대 24×6×480 ≈ 69k자. 코드 424행이 `"MYMEMORY WARNING"` 문자열을 검사하는 것 자체가 한도 초과를 겪었다는 흔적. 실측 응답에 `quotaFinished: false` 필드가 있어 한도 상태를 알 수 있다.
- **Decision**: `previous.messages`에서 `(url, 원문 해시)` → `text_ko` 캐시. 히트면 호출 생략. 하루 대부분의 실행에서 호출 0건.

### B3. 워크플로우 push 충돌·무한 대기 (확인됨)

- **증거**: `update.yml:34-36` `git add → commit → push`. `pull --rebase` 없음. README 49행이 "로컬에서 push하기 전에 `git pull --rebase`가 필요"라고 사람에게만 요구한다 — 반대 방향(사람이 먼저 push)에서 봇 실행이 non-fast-forward로 실패. `timeout-minutes` 없음 → 기본 360분. FIRMS 7일 CSV는 `timeout=180` × 3회 재시도, 외교부도 3회 재시도 → 소스 몇 개가 매달리면 Actions 시간을 크게 태운다(공개 저장소라 무료지만 다음 실행이 `concurrency`에 걸려 밀린다).
- **Decision**: `git pull --rebase -X theirs origin main` (충돌 시 봇 값 우선), `timeout-minutes: 15`.

### B4. stale의 나이를 알 수 없다 (확인됨)

- **증거**: `carry_over`(176-180)는 `fetched_at`을 *실패한* 시도 시각으로 덮어쓴다. 마지막 성공 시각은 어디에도 없다. 화면은 "(이전 값)"만 표시.
- **Decision**: 성공 시 `last_ok_at` 기록. `carry_over`의 `kept`는 `ok/error/fetched_at`만 빼므로 자동 보존. 프론트에서 경과 표시.

### B5. flights가 재시도 헬퍼를 안 쓴다 (내 코드)

- `requests.get` 직접 호출. 다른 소스는 `get()`으로 ConnectionError/Timeout 3회 재시도. 통일.
